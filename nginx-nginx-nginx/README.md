# 🛡️ Dynamic Nginx Proxy Chain & Spoofing Protection Stand

![Docker Compose](https://ttow0130.pages.labranet.jamk.fi/03.-Containerisation/02.docker-compose/)
![Nginx](https://shields.io)
![Python](https://shields.io)

Архитектурный стенд, эмулирующий работу каскада обратных прокси-серверов (Reverse Proxy) с балансировкой нагрузки Round-Robin, сквозной валидацией сетевых заголовков и защитой от подмены IP-адресов (**IP Spoofing**) на любом этапе прохождения трафика.

---

## 🏗️ Архитектура сетевых потоков
```
Трафик внутри изолированной Docker-сети `xffnet` (`172.28.0.0/24`) движется по следующей схеме:

[Внешний Клиент] (Реальный IP: 172.28.0.1, Спуфинг: XFF: 9.9.9.9)
    │
    ▼ 
(Порт 8080)
┌───────────┐
│    lb     │ ──► Балансировщик (172.28.0.10). Полностью игнорирует входящий XFF.
└───────────┘     Фиксирует IP соединения в заголовке X-Real-IP: 172.28.0.1.
│
├───────────────────────┼───────────────────────┐
▼ (Round-Robin)         ▼ (Round-Robin)         ▼ (Round-Robin)
┌───────────┐           ┌───────────┐           ┌───────────┐
│  nginx1   │           │  nginx2   │           │  nginx3   │
└───────────┘           └───────────┘           └───────────┘
   │                         │                       │
   ▼                         ▼                       ▼
[nginx2 -> nginx3 -> app]   [nginx3 -> app]         [app:8000]
```
### Ключевые механизмы:
1. **Dumb LB (`lb`)**: Выступает внешней точкой входа. Принудительно пишет адрес шлюза Docker в `X-Real-IP`, изолируя внутренний периметр от заголовков пользователя.
2. **Шаблонизация (`proxy.conf.template`)**: Прокси-воркеры используют единый универсальный шаблон конфигурации. Переменная `${NEXT_UPSTREAM}` подставляется Docker-ом динамически.
3. **Многоуровневый Маппинг (`map`)**: 
   * **Валидация контента**: Если заголовок `XFF` содержит внешний IP (например, `9.9.9.9`), он мгновенно сбрасывается. Пропускаются только заголовки, начинающиеся с доверенной подсети `172.28.0.`.
   * **Проверка отправителя**: Если запрос пришел от LB — цепочка строится с чистого листа. Если от соседа по Docker-сети — к очищенной строке дописывается его физический IP.
   * **Коррекция строки**: Специфическое регулярное выражение `~^,*(.+)` гарантирует удаление ведущих запятых и артефактов пробелов при обнулении мусора.

## ⚡ Быстрый старт

1. Разверните инфраструктуру стенда в фоновом режиме:
   ```bash
   docker compose up -d --build
   ```
2. Убедитесь, что все сервисы успешно запустились и имеют статус `Up`:
   ```bash
   docker compose ps
   ```

## 🧪 Протокол автоматизированного тестирования

В корень проекта интегрирован bash-скрипт проверки. Он тестирует как штатное поведение балансировщика, так и экстремальные сценарии (прямые запросы к воркерам в обход LB с попыткой пробросить мусорный IP).

Для проверки всех сценариев выполните:
```bash
chmod +x test_stand.sh
./test_stand.sh
```

### Сводная таблица сценариев тестирования:


| № | Сценарий проверки | Команда / Сценарий скрипта | Результат валидации |
|---|---|---|---|
| **1** | **Обычный запрос через LB** | `curl -s http://localhost:8080/` | Выводится честная цепочка прохождения трафика. В начале всегда легитимный IP шлюза (`172.28.0.1`), далее — IP промежуточных прокси воркеров (зависит от шага Round-Robin). |
| **2** | **Защита от Spoofing (Внешний)** | `curl -s -H "X-Forwarded-For: 9.9.9.9" http://localhost:8080/` | **ЗАЩИЩЕНО**. Внешний фейк `9.9.9.9` полностью удален из заголовков на первом же прокси. |
| **3** | **Эмуляция внутренней цепочки** | `wget --header="X-Real-IP: 172.28.0.10" http://nginx3/` | Эмулирует доверенный проброс пакетов внутри сети Docker между узлами `nginx1 -> nginx3`. |
| **Ф** | **Финальный тест (Прямая атака)** | `docker exec -it nginx1 curl -s -H "X-Forwarded-For: 9.9.9.9, 172.28.0.1" http://nginx3/` | **ЗАЩИЩЕНО**. При попытке отправить мусор напрямую на `nginx3` минуя LB, заголовок очищается. Результат приложения: `172.28.0.11` (строго IP отправителя пакета, без запятых и без `9.9.9.9`). |

## 🛠️ Инфраструктурные ограничения (Production-Ready)

Для предотвращения деградации хост-системы при высокой утилизации сети к контейнерам применены жесткие лимиты:
* **Ресурсы**: Каждый Nginx-воркер и Python-приложение ограничены `cpus: '0.5'` и `memory: 128M`.
* **Логирование**: Включен драйвер `json-file` с автоматической ротацией логов (максимум 3 файла по 10 мегабайт на один контейнер) для защиты дискового пространства.
