Документация APP:

Mock-сервер для валидации сетевых заголовков

Данный компонент представляет собой тестовое микроприложение (Mock-сервер),
 написанное на языке Python 3.12 без использования сторонних фреймворков.
  Приложение выполняет роль конечной точки (Upstream/Backend) в цепочке проксирования
   и служит для аудита заголовков HTTP-запросов.

Архитектурные особенности и стекСтек:
Python 3.12 (Alpine-база).
Модули:
Используются исключительно стандартные библиотеки http.server (HTTPServer, BaseHTTPRequestHandler).
    Это гарантирует минимальный размер Docker-образа, отсутствие уязвимостей
    в сторонних зависимостях и мгновенный запуск.

Сетевой интерфейс:
Сервер слушает на адресе 0.0.0.0 (все сетевые интерфейсы контейнера) на порту 8000.
Принцип работы и логика обработки
Приложение обрабатывает только входящие GET-запросы. Логика работы состоит из четырех
    последовательных шагов:Формирование HTTP-ответа: Сервер возвращает статус 200 OK.

Установка заголовков ответа:
Принудительно задается заголовок Content-type: text/plain; charset=utf-8. 
Формат Plain Text выбран для удобства чтения вывода через утилиту curl в консоли.

Парсинг цепочки прокси:
С помощью метода self.headers.get() скрипт извлекает значение заголовка X-Forwarded-For.
    Если запрос пришел напрямую (минуя прокси) и заголовок отсутствует, переменной 
    присваивается дефолтное безопасное значение "Заголовок отсутствует".

Вывод данных:
Сервер кодирует строку ответа в UTF-8 и отправляет её клиенту. В ответе возвращается
    вся накопленная серверами Nginx цепочка IP-адресов.

Безопасность и Production-микроклимат
Несмотря на то, что это тестовый скрипт, в связке с созданным docker-compose.yml он 
    работает по строгим правилам безопасности:
Принцип наименьших привилегий (Least Privilege):
Скрипт выполняется в изолированном пространстве под пользователем guest (UID 1000).
    Даже если в стандартной библиотеке Python обнаружится критическая уязвимость (RCE),
    злоумышленник не сможет получить доступ к root-правам внутри контейнера.

Иммунитет файловой системы:
Так как контейнер монтирует папку со скриптом в режиме ro (Read-Only),
    процесс Python физически не может модифицировать свой код, создавать
     временные вредоносные файлы или логи на диске. Все логи пишутся
     строго в stdout/stderr и перехватываются демоном Docker.
